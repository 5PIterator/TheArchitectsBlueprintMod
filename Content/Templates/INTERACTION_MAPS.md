# Interaction Maps and Discovery

Interaction maps tell The Architect's Blueprint which items can create or modify tiles, walls, liquids, wires, and paint during a paste. You can **discover** vanilla and modded interactions automatically, **edit** curated overrides by hand, and **compile** the result into maps the paste engine uses at runtime.

## How it works

1. **SourceMaps** — JSON files in your save folder (`TheArchitectsBlueprintMod/SourceMaps/`). Some are editable by you; others are generated by discovery commands.
2. **Discovery** — Scans Terraria content (placement rules, wands, rubble tools, paint, plants, conversions, biomes, shimmer) and writes generated SourceMaps.
3. **Compile** — Merges enabled SourceMaps into **CompiledMaps** (`InteractionMap.itr` + `InteractionMap.itr.json`), which the paste system reads when resolving item costs and placement rules.

In multiplayer, discovery and compile are **host / dedicated-server only**. Remote clients use the server's compiled maps.

### Quick workflow

1. Edit hand-curated files: `Custom.itr.json`, `BiomeConfig.itr.json`, `BaseContext.itr.json`.
2. Run discovery for anything that changed — see [Commands and files](#commands-and-files), or `/tab.discAll` for everything.
3. Run `/tab.compile` to rebuild compiled maps (or `/tab.discAllcpl` to discover and compile in one step).
4. Toggle which SourceMap layers are included via **Mod Configuration → Tile Mapping** before compiling.

## File Structure

All SourceMaps are JSON files with the **`.itr.json`** extension and a **metadata + data wrapper**:

```json
{
  "metadata": {
    "format": "tile-first" | "item-first",
    "mapType": "placement" | "biome" | "custom" | "biomeConfig" | "baseContext" | "compiled" | "shimmer" | "wand" | "rubble",
    "modVersion": "...",
    "terrariaVersion": "...",
    "generatedAt": "2025-02-28T..."
  },
  "data": { ... }
}
```

The `metadata` identifies the file by content (format, mapType). The `data` object holds the actual content. All interaction maps use this structure and are found by metadata.

---

## `.itr` vs `.itr.json`

Both extensions refer to **interaction map** files, but they use different encodings and appear at different stages of the pipeline.

| | **`.itr.json`** | **`.itr`** |
|---|----------------|------------|
| **Format** | Human-readable JSON text | Compact binary (tModLoader TagIO, compressed) |
| **Where** | **SourceMaps** — all discovery output and hand-edited maps | **CompiledMaps** — `InteractionMap.itr` only |
| **Purpose** | Edit, inspect, version-control | Fast load at paste time |
| **Written by** | Discovery commands; your manual edits; compile (as a readable mirror) | Compile only |
| **Read by** | Compile (`/tab.compile` merges SourceMaps) | Paste engine (preferred at runtime) |

**SourceMaps use `.itr.json` only.** Discovery and compile never write plain `.itr` files into SourceMaps. If you have leftover `Something.itr` files there from an older version, the mod renames them to `Something.itr.json` on launch.

**CompiledMaps get both files from `/tab.compile`:**
- `InteractionMap.itr` — binary; loaded first when a paste starts
- `InteractionMap.itr.json` — same data in readable JSON; used as a fallback if the binary file is missing or fails to load

You edit SourceMaps as `.itr.json`. You do not need to touch compiled `.itr` files directly — re-run `/tab.compile` after changing SourceMaps.

## Editing SourceMaps

Any `.itr.json` file in SourceMaps can be **edited by hand**, and you can **create new ones**. At compile time, maps are matched by `metadata.mapType` (and `format`), not by filename — so you can rename files freely as long as the metadata stays valid.

Compile loads these map types (when enabled in config): `custom`, `wand`, `rubble`, `paint`, `plant`, `placement`, `conversion`, `biome`, `shimmer`. Config-only files `biomeConfig` and `baseContext` are read by discovery but are not merged at compile.

**`Custom.itr.json` is never overwritten by discovery.** Neither are `BiomeConfig.itr.json` or `BaseContext.itr.json` — discovery reads them as inputs only. Hand-edits to generated maps survive until you run the matching discovery command again. To keep custom rules permanently, put them in `Custom.itr.json` (loaded first at compile, so curated entries take priority over generated ones for the same item).

If two files share the same `metadata.mapType`, compile uses whichever file is found first in the folder — avoid duplicate map types unless you intend to replace one file with another.

## Commands and files

## Unified Interaction Format

All interaction maps use the **same per-interaction fields**. The only difference is whether the map is **item-first** or **tile-first**:

| Map type | Key | Interaction fields |
|----------|-----|--------------------|
| **Item-first** | Item name | `layer`, `main`, `base`, `style`, `yield`, `ammo` |
| **Tile-first** | Tile/wall/liquid name | `layer`, `item`, `base`, `style`, `yield`, `ammo` |

In tile-first maps, the main result is the key (the tile being described). Each interaction specifies `layer` to interpret the main. In item-first maps, the item is the key, so each interaction specifies `layer` and `main` (the result).

---

### Per-interaction fields

| Field | Required | Default | Description |
|-------|----------|---------|-------------|
| `layer` | Yes | — | `"Tile"` \| `"Wall"` \| `"Liquid"` \| `"Wire"` \| `"Paint"` |
| `main` | Yes (item-first) | — | Resulting tile, wall, liquid, wire, or paint. |
| `item` | Yes (tile-first) | — | The item that can create this tile/wall/liquid. |
| `base` | No | omitted | Source tile/wall the item must interact with. Omit for direct placement. |
| `style` | No | omitted | Placement style (e.g. torch variant). Use `-1` for style-agnostic. |
| `yield` | No | `1` | Stack debits per placement. Omitted or null = one per item. `-1` (or any `≤ 0`) = infinite — no stack debit. |
| `ammo` | No | tool item | Consumable debited instead of the tool (`AmmoId ?? ItemId`). Omit when the tool item itself is consumed. |
| `alias` | No | omitted | Alternate tool item names accepted when the primary item is missing (e.g. Rubblemaker modes). |
| `fake` | No | omitted | Tile/wall actually placed when different from `main` (e.g. Echo rubble for a natural ambient main). |

Missing required fields are skipped at load time and logged. Check the compile debug log if entries are missing.

Each layer interprets `base` and `main` differently:
- **Tile**: `base` = source tile, `main` = result tile
- **Wall**: `base` = source wall, `main` = result wall
- **Liquid**: `main` = result liquid type
- **Wire**: `main` = result wire kind
- **Paint**: `main` = result paint ID

### Item-first examples

Keys are **item internal names** (e.g. `"CorruptSeeds"`, `"WaterBucket"`). Each item has an `interactions` array.

**Seed (converts existing tile):**
```json
"CorruptSeeds": {
  "interactions": [
    {
      "layer": "Tile",
      "base": "Dirt",
      "main": "CorruptGrass",
      "yield": 1
    }
  ]
}
```

**Bucket (direct placement):**
```json
"WaterBucket": {
  "interactions": [
    {
      "layer": "Liquid",
      "main": "Water",
      "yield": 10
    }
  ]
}
```

**Tool with ammo (e.g. Living Wood Wand):**
```json
"LivingWoodWand": {
  "interactions": [
    {
      "layer": "Tile",
      "main": "LivingWood",
      "yield": 1,
      "ammo": "Wood"
    }
  ]
}
```

**Infinite-yield tool (e.g. Spectre paint brush):**
```json
"SpectrePaintbrush": {
  "interactions": [
    {
      "layer": "Paint",
      "main": "RedPaint",
      "yield": -1
    }
  ]
}
```

**Rubblemaker with tool alias and Echo fake:**
```json
"Rubblemaker": {
  "interactions": [
    {
      "layer": "Tile",
      "main": "SmallPiles",
      "fake": "SmallPiles1x1Echo",
      "style": 0,
      "yield": 1,
      "ammo": "StoneBlock",
      "alias": ["RubblemakerMedium", "RubblemakerLarge"]
    }
  ]
}
```

Lookup uses `main`; placement uses `fake` when set. `alias` lists alternate tool item types that also satisfy the tool (Rubblemaker size modes).

---

### Tile-first maps (generated)

Keys are **tile/wall/liquid names** (e.g. `"Dirt"`, `"Stone"`). Each entry has an `interactions` array:

```json
"Dirt": {
  "interactions": [
    {
      "layer": "Tile",
      "item": "DirtBlock",
      "style": 0
    }
  ]
}
```

Omit `base`, `ammo`, and `yield` for a standard one-block-per-item placement. Use `"yield": -1` when the item should not debit stacks.

For compact `itemNames` format, `layer` is at the value level:

```json
"StoneWall": {
  "layer": "Wall",
  "itemNames": ["StoneWall", "WoodWall"]
}
```

---

### BiomeConfig.itr.json (mapType=biomeConfig)

Configures items used by **BiomeDiscovery** (run `/tab.discBiome` to generate `Biome.itr.json`). The `data` object has item names as keys; values have:

| Field | Description |
|-------|-------------|
| `type` | BiomeConversionID: `0`=Purity, `1`=Corruption, `2`=Hallow, `3`=GlowingMushroom, `4`=Crimson, `5`=Sand, `6`=Snow, `7`=Dirt, `8`=PurificationPowder, `10`=Chlorophyte |
| `yield` | Blocks converted per item (e.g. `5` for powder, `50` for solution) |

Keys use **internal names** (e.g. `GreenSolution`, not "Green Solution"):

```json
"GreenSolution": { "type": 0, "yield": 50 }
```

---

### BaseContext.itr.json (mapType=baseContext)

Array of tile names used as fallback for **placement discovery**. The `data` array lists tiles to test when an item's `createTile` requires a base (e.g. seeds on dirt). Add tiles commonly used as conversion targets:

```json
{
  "metadata": { "format": "item-first", "mapType": "baseContext" },
  "data": ["Dirt", "Mud", "Stone", "Ash", "GrayBrick"]
}
```

---

## Name Resolution

- **Item names**: Use internal names (e.g. `WaterBucket`, `PurificationPowder`, `GreenSolution`) or `ModName/ItemName` for modded items.
- **Tile/wall names**: Use internal names (e.g. `"Dirt"`, `"CorruptGrass"`). Vanilla names are in the template; modded tiles use `ModName/TileName`.

Unresolved names are skipped at load time and logged. Check the compile debug log if entries are missing.
